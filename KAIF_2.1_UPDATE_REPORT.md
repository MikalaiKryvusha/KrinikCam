## 2. Грабли — каждая с дословной ошибкой и воспроизведением

### Г1 (критично). Безаргументный запуск ядра = `install` → задание перезаписано, часть работы утеряна

**Что сделал:** хотел посмотреть список подкоманд и выполнил `node .kaif/kaif-core.mjs`.

**Дословно на выходе** (ошибки нет — операция прошла «успешно»):
```
⟳ existing KAIF 2.1 detected — running as an UPDATE to 2.1 (existing files are kept, new ones added)
⟳ bootstrap classified against the surviving deploy manifest: 0 replaced, 0 modules merged in-place, 0 added, 62 kept
+ wrote KAIF_UPDATE_TASK.md (6 items, ...)
```
и в шапке нового задания: `> re-run on 2.1: the tree already carries this version — verify the previous merge rather than redoing it.`

**Цена:** из задания исчезли **2 пункта** — `owner-conventions` (STATUS/EXPERIENCE) и `stale-claims`
(46 адресов строк), **вся секция «What's new in the templates»** (обе версии новостей — единственный
источник, по которому агент понимает, ЧТО вносить в translated-файлы) и **2 модульных диффа**
(`pause` `<preamble>`, `programming` fraud table). Осталось 6 пунктов и «(no template notes recorded
for this interval)». Я восстановил файл только потому, что успел прочитать его целиком раньше и текст
лежал в контексте сессии; сессия, которая сделала бы то же самое на пять минут позже, потеряла бы
работу молча и никогда бы не узнала о двух пунктах.

**Почему это не защищено:** защита есть, но включается позже —
`= kept existing KAIF_UPDATE_TASK.md (it carries recorded checkpoints — not overwritten)`.
Файл беззащитен ровно в окне «сгенерирован → первый чекпоинт», то есть на всём протяжении реальной работы.

**Воспроизведение:**
```bash
node KAIF-LOADER.mjs --lang ru --mode standard   # получили задание на 8 пунктов
wc -l KAIF_UPDATE_TASK.md
node .kaif/kaif-core.mjs                          # без аргументов, без флагов, без подтверждения
wc -l KAIF_UPDATE_TASK.md                         # пунктов меньше, новостей нет
```

**Предложение:** (1) пустая команда → печатать usage и выходить, как это уже делается для неизвестной
(`✖ unknown command: help (install | check | ...)`); `install` не должен быть дефолтом деструктивной
операции; (2) перед перезаписью задания без чекпоинтов — сохранять предыдущее в
`KAIF_UPDATE_TASK.superseded.md` (имя уже зарезервировано в `.gitignore`, механизм напрашивается сам);
(3) при re-run на той же версии — не перегенерировать задание вообще, а печатать «задание уже есть».

### Г2 (критично). Модульный мерж в переведённом развёртывании породил ДВУХГОЛОВЫЕ навыки

Классификатор i18n отработал на 20 навыках («is translated wholesale … kept intact»), но **на двух
файлах дал ложноотрицательный результат** и слил в них модули шаблона:
```
↻ merged 3 module(s) into .claude/skills/kaif-remove/SKILL.md (1 kept for you)
↻ merged 4 module(s) into .claude/skills/pause/SKILL.md (2 kept for you)
```
Результат: **английский шаблон целиком вставлен ПОВЕРХ русской процедуры**, между frontmatter и
русским H1. Оба файла стали самопротиворечивыми:

- **`/pause`** — сверху английские шаги «make a local commit **without pushing**», «Do NOT update
  `STATUS.md`, README», снизу русские «Шаг 5. Коммит и пуш в GitHub», «Шаг 2. Актуализировать README.md».
  Один навык, два взаимоисключающих предписания, оба выглядят каноничными.
- **`/kaif-remove`** — 50 строк английского дубликата ПОЛНОЙ процедуры удаления фреймворка («## Two
  modes», «## Procedure» с 5 шагами) перед русской процедурой. Это **деструктивный** навык: агент,
  читающий файл сверху, исполнит английскую ветку, не дойдя до русской.

**Ни один гейт этого не видит:** `check` проверяет присутствие файлов и sha зеркал, `update-verify`
пересинхронизирует зеркала — оба зелёные на двухголовом файле. Нашли: я (в `/pause`, глазами при
разводе навыков) и состязательный скептик воркфлоу (в `/kaif-remove`, вердикт «blocker», исправлено).

**Воспроизведение:** развернуть KAIF с `--lang ru`, перевести `.claude/skills/pause/SKILL.md` целиком,
оставив английским только `name:` во frontmatter, обновиться на 2.1 → в файле два H1 и две процедуры.
Детектор для чужих проектов: `for f in .claude/skills/*/SKILL.md; do [ $(grep -c '^# ' $f) -gt 1 ] && echo $f; done`.

**Предложение:** для развёртывания с `"i18n": "translated"` вставка НОВОГО модуля в файл должна быть
**запрещена машинерией** (только в задание, как дифф). Вставлять английский модуль в переведённый файл
всегда неверно: либо агент переведёт его сам, либо не заметит. Плюс дешёвый гард в `check`: «>1 H1 в
SKILL.md» и «блок латиницы >200 символов в файле развёртывания с `language: ru`».

### Г3 (главное по трудозатратам). `merge-diverged` выдаёт список файлов без диффов — 23 задачи вслепую

Задание по каждому из 23 файлов говорит ровно одно и то же:
`AGENT_GUIDE.md (translated wholesale — its headings are in the owner's language, a by-signature merge
is impossible; fold the news in by hand)`.

Чего в задании нет: **что именно изменилось в шаблоне этого файла между 1.6 и 2.1**. Есть только общий
список новостей релиза на весь фреймворк. Агент обязан догадаться, какие из ~30 пунктов новостей
относятся к его файлу, и не имеет способа проверить, что ничего не пропустил.

**Что пришлось сделать руками:** скачать `KAIF-CORE-BUNDLE.md` релиза **v1.6** (425 708 Б), написать
парсер `FILE:`-блоков (фенсы переменной длины — от ``` до ``````), распаковать 134 + 147 шаблонов и
построить 38 unified-диффов. Только после этого стало видно главное:

> **8 файлов из 23 в списке `merge-diverged` не требовали НИЧЕГО** — их шаблоны байт-идентичны между
> 1.6 и 2.1: `PHILOSOPHY.md`, `bug-research`, `check-backlog`, `experience`, `fix-vision`,
> `refresh-context`, `revision`, `what-next`.

То есть **35 % пунктов самого дорогого раздела задания — пустые**, и узнать это можно только тем
способом, которым машинерия и так владеет: у неё был baseline v1.6 (она сама написала
«⟳ synthetic baseline: v1.6's own KAIF-CORE-BUNDLE.md (52 templates)»).

**Предложение к 2.2 (приоритет №1):** в `merge-diverged` для каждого файла давать (а) флаг «шаблон
между версиями НЕ менялся — действий не требуется» и (б) unified-дифф шаблона `old→new` — ровно в том
формате, в каком он уже даётся для `merge-modules`. Это превращает 23 туманных пункта в 15 конкретных
и убирает необходимость качать предыдущий релиз.

### Г4. `stale-claims`: кап 40 хитов, забитый шумом зеркал, пропустил единственный публичный клейм

Сканер выдал 46 строк. Из них **44 — атрибуции правил**, которые менять НЕЛЬЗЯ:
`**Правило одного шага (KAIF 1.6):** …` — правило действительно введено в 1.6, переписывать его в
«2.1» значит подделывать историю. Настоящих клеймов версии развёртывания в списке два: `AGENTS.md:3`
и (косвенно) навыки-зеркала.

При этом шум умножается на 5: одно и то же правило присутствует в `.claude/`, `.agents/`, `.grok/`,
`.cline/`, `.roo/` — зеркала, которые машинерия **сама** пересинхронизирует на `update-verify`, но
которые она же вываливает агенту как работу.

**Что сканер пропустил** — публичный бейдж на витрине проекта:
```
README.md:8  [![Framework: KAIF 1.6](https://img.shields.io/badge/Framework-KAIF%201.6-6E56CF.svg)]
```
Ровно тот класс, ради которого сканер и написан (в комментарии кода: *«Unliminium counted 12 documents
still asserting the OLD version after a green update, 3 of them on the public storefront»*). Причина —
`if (hits.length >= 40) return hits;` в `scanStaleClaims`: квоту выбрали зеркала, до `README.md` обход
не дошёл. Нашёл я это грепом вручную, уже после того, как чекпоинт `stale-claims` можно было спокойно
проставить зелёным.

**Предложение:** (1) не сканировать зеркала вовсе — они производные; (2) различать классы: строка вида
`(KAIF <ver>)` в скобках после правила — атрибуция, а `KAIF <ver>` в заголовке, бейдже, фразе «обвязан
/ wrapped by» — клейм; (3) кап не по числу хитов, а по числу файлов, и с явным «показаны N из M».

### Г5. Ложные модульные диффы из-за дрейфа H1-сигнатуры

Четыре README директорий знаний попали в `merge-modules` с формулировкой
`an H1 module may not be inserted next to an existing H1 — placeholder-signature drift, reconcile by
hand (bug 26)`. Проверка по бандлам: шаблоны `plans/README.md`, `ideas/README.md`,
`researches/README.md` **байт-идентичны между 1.6 и 2.1** — вносить было нечего. Сигнатурой служит текст
заголовка, а у нас он переведён («# `plans/` — детальные планы работ» против «# `plans/` — детальные
пошаговые планы»), поэтому машинерия сочла модуль отсутствующим и предложила «вставить» весь файл.
Настоящее изменение было только у `homeworks/README.md` (+7 строк про ДЗ класса вкуса) — оно и внесено.

**Предложение:** совместить с Г3 — если шаблон файла между версиями не менялся, модульный дифф не
выдавать в принципе, каким бы ни был дрейф сигнатур.

### Г6. `checkpoint judge --verdict "…"` требует текст в аргументе командной строки

Это противоречит правилу, которое **сам же релиз 2.1 внёс в канон**: «TEXT TRAVELS THROUGH FILES, NEVER
THROUGH COMMAND-LINE ARGUMENTS». Вердикт судьи — многострочный текст на языке владельца (у нас
кириллица, кавычки-ёлочки, стрелки), и единственный способ его записать — то, от чего канон
предостерегает. На macOS/zsh прошло, на Windows PowerShell 5 это ровно «лицо 1» из четырёх,
описанных в новом разделе гигиены.

**Предложение:** `checkpoint judge --verdict-file <path>` (аргумент-путь), а строковый вариант оставить
для ASCII-односложных случаев.

### Г7. `kaif-provenance.mjs`: `check` и `report` расходятся в том, что считать каноном

При **незаявленных** `canonArtifacts` (у нас в `.kaif/kaif.json` их нет):
- `report` → `no canonArtifacts declared in .kaif/kaif.json — nothing to report` (exit 0);
- `check` → сканирует проект и падает с exit 1 на четырёх находках.

Одна и та же неконфигурированность даёт «нечего проверять» в одной подкоманде и «проверка провалена»
в другой. Сами находки, к слову, полезные, но это не фрод, а расхождение конвенций: у нас марка
`[AI]` исторически ставится **в заголовке секции** (`### [AI] Что это значит инженерно (ждёт сверки
Криника)`), а гейт 2.0 требует строго парный инлайн-блок и запрещает вложенность:
```
✖ ideas/43_stream_keepalive_respectful.md:119 — [AI] opened while [AI] from line 73 is still open (nesting is not allowed)
✖ interviews/interview_011_network_resilience.md:300 — stray [/AI] with no open mark
```
Канон 1.6, который эти марки вводил, заголовочный стиль не запрещал. Мы гейт не подключали, документы
Криника не трогали — оставили ему как вопрос.

**Предложение:** `check` без объявленного канона должен вести себя как `report` (exit 0 + подсказка);
и отдельно — либо разрешить заголовочную форму марки, либо сказать в каноне 1.6-эпохи, что она
незаконна, потому что проекты уже наставили её сотнями.

### Г8. `kaif-canon-lint.mjs selftest` без правил возвращает 0 — риск вечнозелёного гейта

Поведение осознанное и прокомментировано в коде (bug 30.2: «a fresh deployment's red selftest is
exactly what agents chase»), спорить не буду — но следствие стоит назвать: проект, честно исполнивший
рекомендацию «повесь `selftest` на свои гейты» ДО сидирования `.kaif/canon-lint-rules.json`, получает
гейт, который зелен всегда и ничего не проверяет. Это тот самый «ложный зелёный», против которого
написан весь TESTING_FRAMEWORK.

**Предложение:** третий код выхода (2 = «не сконфигурировано») или флаг `--require-configured`, чтобы
CI мог отличить «правил нет» от «правила прошли».

### Г9. Мелочи

- `node .kaif/kaif-core.mjs help` → `✖ unknown command: help` (usage печатается, но статус ошибочный).
- `KAIF_UPDATE_TASK.md` добавлен в `.gitignore` — значит чекпоинты и вердикт судьи **не попадают в
  историю git**; доказательством обновления остаётся только `.kaif/last-update.json`. Для проекта, где
  канон требует «judge перед каждым push», было бы логичнее коммитить задание с чекпоинтами.
- Первый прогон сообщил `8 module(s) await your merge`, а в разделе диффов их 8 при 7 файлах —
  формулировка «module(s)» против списка «файл (N)» читается неоднозначно.

## 3. Что из новинок 2.1/2.0 реально потрогал и как оно себя повело

| Новинка | Трогал? | Как себя повело |
|---|---|---|
| Тонкий `KAIF.md` + лоадер + sha256-гейт | да | Безупречно. exit 0 за ~40 с, обе чексуммы сошлись, машинерия сама распознала легаси-1.6 и пошла путём update-by-bootstrap. Ручной дифф-миграции (как в 1.4-эпоху) действительно больше нет. |
| Синтетический baseline для легаси | да | Заявлено «the legacy path is no longer blind» — и это правда для классификации (7/12/13/43), но **не** для задания: диффы translated-файлов до агента не доехали (Г3). |

### Дополнительные грабли, вскрытые судом

**Г10. Неизвестный флаг у мутирующей команды игнорируется молча.** `sync --dry-run` выполнил реальную
запись 145 файлов. Предложение: неизвестный флаг → отказ с кодом 1; либо реализовать `--dry-run` для
всех мутирующих подкоманд.

**Г11. `check` возвращает exit 0 при разошедшихся зеркалах.** Дословно:
`⚠ 76 mirror copies lag the canon … ✅ manifest satisfied: 65 files + 140 agent artifacts present`,
`echo $?` → `0`. Формально это «нормально до re-sync», но фактически в окне между `update` и
`update-verify` проект живёт с ПЯТЬЮ агентскими системами, у которых один и тот же навык предписывает
противоположное (`/pause`: «не пушь» в `.claude` против «собери APK, закоммить и запушь» в `.cline`).
Пункт задания `recheck` при этом требует «the deployed manifest must be **100 % green**» — и его можно
честно закрыть в этом состоянии. Предложение: либо `check` красный при дрейфе зеркал (с подсказкой
`sync`), либо чекпоинт `recheck` сам прогоняет `sync` перед проверкой.

**Г12. Рассинхрон внутри самих шаблонов 2.1.** Шаблон `EXPERIENCE.md` объявил `Repro` обязательным и
ввёл `Trigger`/`mechanized`, а шаблон навыка `/experience`, который этот файл ведёт, остался прежним
(он даже не попал в список изменившихся: его sha в 1.6 и 2.1 совпадают). Это ровно та пара
«источник ↔ зеркало», реестр которых 2.1 вводит в канон — только разъехавшаяся у автора фреймворка.

**Г13. Аудит модулей в переведённом проекте нечитаем.** `update-verify` печатает
`33 modules differ, 216 template modules absent, 298 modules are yours` и десяток строк
`MODULE ABSENT: AGENT_GUIDE.md :: ### Planning discipline …`. Для i18n-развёртывания «absent» — норма
(сигнатура переведена), но отличить её от РЕАЛЬНОЙ потери модуля по выводу невозможно. Предложение:
для `"i18n": "translated"` не печатать `MODULE ABSENT` как дефект, либо помечать «ожидаемо для
переведённого развёртывания».

## 5. Пожелания к 2.2 (по убыванию цены)

1. **Диффы шаблонов для `merge-diverged`** и явная отметка «шаблон не менялся» (Г3). Это единственный
   пункт, который сегодня заставляет агента качать предыдущий релиз и писать парсер бандла. 8 из 23
   пунктов нашего задания были пустыми, и узнать это можно было только так.
2. **Запретить вставку новых модулей в файлы `"i18n": "translated"`** (Г2) + гард на «>1 H1 в SKILL.md».
   Двухголовый деструктивный навык — худший из возможных исходов «зелёного» обновления.
3. **Пустая команда ядра не должна быть `install`** и задание без чекпоинтов не должно перезаписываться
   молча (Г1). Одна опечатка стоила двух пунктов задания и всех новостей релиза.
4. **`stale-claims`: не сканировать зеркала, различать атрибуцию и клейм, кап по файлам** (Г4). Сейчас
   отношение сигнал/шум — 2 к 46, а единственный публичный клейм в выдачу не попал.
5. **`--verdict-file`** вместо текста в CLI-аргументе (Г6) — фреймворк не должен нарушать правило,
   которое сам ввёл в том же релизе.
6. **Согласовать `provenance check` и `report`** при незаявленном каноне; определиться с легальностью
   заголовочной формы марки `[AI]` (Г7).
7. **Отличать «линтер не сконфигурирован» от «линтер прошёл»** кодом выхода (Г8).
8. **Помощь в миграции летописи:** машинерия видит `researches/`+`STATUS.md` и может подсказать
   кандидатов на перенос (файлы с «archive/архив» в имени, секции STATUS с закрытыми датами). Сейчас
   это чисто ручная археология, а правило «переносить дословно» без инструмента исполняют не все.
9. **`check` не должен быть зелёным при дрейфе зеркал** — или `recheck` должен сам звать `sync` (Г11).
   Сейчас пункт задания, требующий «100 % green», честно закрывается на дереве, где пять агентских
   систем предписывают противоположные вещи.
10. **Неизвестный флаг у мутирующей команды — отказ, а не молчаливое исполнение** (Г10).
11. **Мерж модулей не трогает frontmatter** — тело навыка переписано, `description` остался от старой
    версии и противоречит ему (Г12 в §4). А `description` — это то, по чему навык маршрутизируется.
12. **Проверить собственные пары «документ ↔ ведущий его навык»** перед релизом: `EXPERIENCE.md`
    изменился, `/experience` — нет; реестр пар из своего же канона 2.1 поймал бы это у автора.
13. **Для i18n-развёртываний не печатать `MODULE ABSENT` как дефект** (Г13): 216 «отсутствующих»
    модулей в переведённом проекте — норма, но неотличимая от реальной потери.
