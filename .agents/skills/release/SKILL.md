# /release — выпуск релиза в GitHub

Криник просит выпустить новую версию KrinikCam. Это **необратимое внешнее действие** (публичный тег +
GitHub Release). Выполняй рутину **по порядку**, между шагами коротко пиши в чат, что делаешь. Если шаг
падает — остановись, покажи ошибку, НЕ продолжай вслепую.

Все пути относительно корня проекта (рабочая машина с 2026-10-17 — Windows: `D:\work\ai_sandbox\KrinikCam`;
прежняя — macOS: `/Users/kryvusha/ai_sandbox/KrinikCam`).

> ⚠️ **ПОДТВЕРЖДЕНИЕ ОБЯЗАТЕЛЬНО.** Перед самим выпуском (шаг 7) покажи Кринику: какая версия будет
> (текущая → новая), что дерево чистое, что собралось. Жми «релизим» только с его явного «да». Релиз =
> публичный тег и Release, откатывать неприятно. В автономном режиме (/autoloop) релиз НЕ выпускать.

## Шаг 0. Решить тип бампа (и имя релиза — остановка по ИДЕНТИЧНОСТИ, а не формальность)

`tools/release.mjs` по умолчанию бампит **minor** (0.3 → 0.4), с флагом `--major` — мажор (0.x → 1.0).
Спроси Криника (или подтверди дефолт): minor или major. RC по умолчанию = minor.

**Если релизу даётся кодовое имя** (короткое запоминающееся имя темы релиза — оно уходит в заголовок и
в хедлайн нот), помни: **имя — это ИДЕНТИЧНОСТЬ, а идентичность авторствует владелец, НИКОГДА не агент,
при ЛЮБОЙ широте одобрения.** Общее «релизь, не спрашивай» снимает ТРЕНИЕ подтверждений на действиях,
но не передаёт АВТОРСТВО того, как продукт себя называет и подаёт (полевой инцидент: при буквальном
«Я ОДОБРЯЮ ВСЁ, не спрашивай» агент придумал кодовое имя релиза, и владелец встретил имя своего
продукта как свершившийся факт). У этой жёсткой остановки ровно три законных исхода:

1. **имя даёт Криник** (или выбирает из предложенных тобой кандидатов);
2. **ты делаешь ВСЁ остальное и задаёшь ОДИН точечный вопрос про имя** — один вопрос внутри уже
   разрешённой работы не стоит ничего и не про это было «не спрашивай»;
3. **выпустить БЕЗ имени** под нейтральным фактическим заголовком (`KrinikCam X.Y`) — ВСЕГДА
   ДОСТУПНЫЙ запасной ход: когда Криник недоступен, релиз не блокируется навсегда, а назвать его
   может только он сам — хоть задним числом. Никогда не имя-заглушка: заглушка — это всё равно имя,
   которое кому-то потом придётся расколдовывать.

**Выпущенное имя несёт артефакт-ИСТОЧНИК** — строку в нотах/плане релиза:
`codename: <владелец · канал · дата>` — так же, как научное утверждение несёт свою ссылку; имя без
автора должно быть невозможно не заметить. А если выпущенное имя оказалось неудачным, агент не
переименовывает по своей инициативе — исправление бренд-ошибки тоже бренд-решение.

## Шаг 1. Пречек окружения (не выпускаем на грязном/сломанном)

```bash
git status --short                      # дерево должно быть ЧИСТЫМ (кроме gitignored apk/pdf)
git branch --show-current               # должно быть main
git pull --rebase                       # подтянуть, чтобы пуш прошёл fast-forward
gh auth status                          # gh залогинен (нужен для GitHub Release)
node tools/version.mjs                  # показать текущую версию
```
Если дерево грязное — сначала закоммить/разберись (можно через `/pause` или `commit.mjs`). На грязном
дереве `release.mjs` закоммитит лишнее в `release: X.Y`.

**Ключ подписи релиза — из `.env` ВНЕ git** (локальное, не KAIF; [OWNER] 2026-10-17, дословно в комментарии
`app/build.gradle.kts`: «в .env заведите ключи для двух сборок: Debug KCAM, KCAM — это будет релизная
сборка без дебаг меню и отладочных инструментов и в R8», «.env ВНЕ ГИТА!!!»). Проверь, что релизная
четвёрка на месте, НЕ печатая значений:

```bash
grep -o '^KCAM_RELEASE_[A-Z_]*' .env    # ждём 4 имени: STORE_FILE · STORE_PASSWORD · KEY_ALIAS · KEY_PASSWORD
git check-ignore .env                    # должно напечатать .env — секреты не в git
```
Нет четвёрки (или нет файла по `KCAM_RELEASE_STORE_FILE`) — Gradle НЕ упадёт, а подпишет release
DEBUG-ключом с `WARNING: KCAM_RELEASE_* в .env не найдены` — такой APK **не публикуем**: стоп, скажи
Кринику. Ключ «Debug KCAM» (`KCAM_DEBUG_*`) — для debug-сборок, к релизу не относится.

В проекте ведётся **реестр пар «источник ↔ зеркало»** (`AGENT_GUIDE.md` → «Гигиена документов и
текста») — прогони команду проверки каждой строки прямо сейчас: релиз, выпущенный поверх разъехавшейся
пары, зашивает расхождение в поставку. Красная строка = остановись и сведи пару до продолжения.

## Шаг 2. Актуализировать README.md (EN/RU)

Открой `README.md` и приведи в соответствие с реальным состоянием: статус фаз, рабочие фичи,
инструкции. README двуязычный (EN/RU) — поддержи оба. Не выдумывай — отражай только то, что реально
сделано и проверено (сверься со `STATUS.md` и закрытыми `bugs/`*_DONE_*, `ideas/`*_DONE_*).

**Номер версии живёт и ВНУТРИ картинок — перерисовывай их командой, а не на глаз** (KAIF 2.4). Витрина
несёт версию там, куда не дотянется текстовый поиск: подпись, вшитая в логотип или баннер, плюс бейдж,
строка версии, alt-текст картинки и самая новая строка таблицы истории версий. У KrinikCam на
2026-10-17 картинок с вшитой версией НЕТ — версия живёт в текстовом бейдже shields.io в шапке
`README.md` (`Version-X.Y`) и в строках таблицы фич (`✅ vX.Y`):

```bash
grep -nE 'Version-[0-9]|✅ v[0-9]' README.md    # каждое попадание — сверить с новой версией
```
Появится картинка с версией — добавь сюда её команду перерисовки, а после прогона ОТКРОЙ картинку и
прочитай подпись глазами. Оплачено в поле на самом origin фреймворка: релиз 2.3 ушёл в GitHub с
логотипом, на котором всё ещё было 2.2, и с README на прошлой версии, потому что подпись нечем было
перерисовать и никто её не открыл.

**А СМЫСЛ кодового имени спрашивают у Криника, никогда не выводят из самого имени** (KAIF 2.4). Если
витрина объясняет, что значит имя версии, — цитируй слово Криника об этом смысле (интервью, журнал
решений, сообщение в чате). Такого слова нет — либо один точечный вопрос, либо не объясняй имя вовсе;
нейтральная подача законна. Оплачено в той же сессии: имя прочитали как правдоподобную метафору, и
догадка разошлась по обеим языковым половинам нот абзацами и заголовками при всех зелёных гардах
витрины.

**README и релиз-ноты — артефакты КРИНИКА, витрина, под которой он подписывается** (KAIF 2.2). Поэтому
если у проекта есть портрет голоса (`AUTHOR_STYLOMETRY.md`, `/owner-voice`), ОТКРОЙ его сейчас и прогони
его самопроверку, прежде чем отдавать текст; портрета нет (у KrinikCam на 2026-10-17 файла нет) —
нет и обязательства, и его отсутствие никогда не краснит релиз. ЧЕРНОВОЙ портрет (пороги не
достигнуты, слепой тест не пройден) — по нему пишут, но НЕ переписывают ИЗ него: режим rewrite с
черновика не стартует. В любом случае вердикт «это звучит как я» принадлежит Кринику — класс вкуса
агент никогда не судит (`TESTING_FRAMEWORK.md`).

**То, что это артефакты владельца, НЕ вносит в них провенанс-марки** (`AGENT_GUIDE.md` → провенанс-марки,
исключение витрины): `README` и релиз-ноты уходят как есть, поэтому никогда не несут `[AI]…[/AI]`. Их
очередь приёмки — ВЫЧИТКА Криника, и она так же обязательна: оформи просьбу как ДЗ в `homeworks/` и
прямо скажи в отчёте о релизе, что текст витрины ещё не вычитан, если это так.

**Витрину судит МАШИНА, а не память** (KAIF 2.2). Правила витрины живут в `AGENT_GUIDE.md` → «The
storefront — text a stranger reads»: никакого текста о самом документе, никаких оправданий рядом с
числом, никакого намёка на закулисье, никакого отрицания, подрывающего цифру, никакой кальки, никакого
безличного голоса в процедуре, никакой внутренней метки как имени строки таблицы, никакого диапазона
оценки шире своего источника, никакой внутренней команды сборки в роли доказательства, никакой
инструкции, которую человек не может выполнить (флаг, который передаёт АГЕНТ, — не то, что читатель
может «добавить»), и две языковые половины должны совпадать по скелету. Линтера витрины у KrinikCam
нет (на 2026-10-17) — пройди десять правил руками по обеим половинам `README.md` и нот, прежде чем
отдавать текст.

## Шаг 6. Judge-проход по релиз-кандидату (ОБЯЗАТЕЛЕН, KAIF 1.5)

Прогони `/fable-judge` по собственным заявлениям релиз-кандидата: каждое утверждение в README/нотах
о том, что работает, должно быть подкреплено НАБЛЮДЕНИЕМ (харнес `ui.mjs`, смоук `tools/smoke.mjs`,
свежие логи, закрытые `bugs/*_DONE_*`), а не памятью сессии. Найдено неподтверждённое заявление или
фрод — сначала фикс и повторный judge, потом выпуск. Релиз — тот артефакт, чьи ложные заявления
увидит весь мир.

## Шаг 6.5. Деплой-чеклист (когда выкат заменяет РАБОТАЮЩУЮ систему; KAIF 1.6)

Если релиз включает деплой поверх живого сервера/контейнера/сервиса — пройди пять гейтов (каждый
существует потому, что его пропуск ронял реальный прод). Для KrinikCam это редкий случай (обычно мы
выпускаем APK, а не заменяем работающий сервис), но если он настал:

1. **Сначала зеркало прода.** Сними ФАКТИЧЕСКУЮ конфигурацию работающего прода ДО замены
   (inspect/env/версия) — прод часто живёт с настройками, которых не помнит ни один документ, и слепой
   редеплой «по докам» молча меняет поведение (или направляет прод на dev-эмулятор). Каждое отличие
   старого запуска от нового — осознанное, названное решение.
2. **Живой смоук.** Запусти новый инстанс и прочитай его первый рабочий цикл в логе своими глазами
   (`TESTING_FRAMEWORK.md` → observation gates).
3. **Самодостаточность артефакта.** Образ/бандл стартует в изоляции, все модули на месте — образ,
   отставший от кода, ронял проды при всех зелёных тестах.
4. **Инварианты домена.** До переключения выпиши числа, которые не должны измениться (количества,
   суммы, размеры); после — сравни.
5. **Документ «боевой запуск».** После деплоя обнови документ репозитория о том, как прод реально
   запускается. Прод-конфигурация, живущая только внутри работающего процесса, — мина, на которую
   наступит следующая сессия.

## Шаг 7. Выпуск (после подтверждения Криника)

```bash
node tools/release.mjs              # minor (0.3 → 0.4); JDK выбирает tools/env.mjs сам
# или:
node tools/release.mjs --major      # major (0.x → 1.0)
```
`release.mjs` делает всё разом: бамп `version.json` (minor/major), `assembleRelease`, переименование APK
в `KrinikCam-vX.Y.apk`, коммит `release: X.Y` + тег `vX.Y`, пуш коммита и тега, `gh release create` с
авто-нотами, очистка APK из корня после загрузки.

> Совет: `node tools/release.mjs --dry-run` покажет, какая версия/тег будут, без сборки и пуша — удобно
> показать Кринику перед реальным выпуском.

## Шаг 7.5. Двуязычные релиз-ноты С ПЕРЕКЛЮЧАТЕЛЯМИ ЯЗЫКА (обязательно)

`release.mjs` создаёт релиз с `--generate-notes` (только ссылка Full Changelog) — это НЕ финал. Ноты
KrinikCam **двуязычные (EN/RU) с якорями-переключателями** (канон с v0.6; Криник следит). Формат:
```markdown
> **Release date: YYYY-MM-DD** · Minsk.

<a name="english"></a>
## English · [Русский](#русский)
… секции EN (🎥 Cameras & scene · 📡 Streaming · 🎞️ Recording · 🌍 Localization · 🐞 Fixes · 📦 Install) …

---
---

<a name="русский"></a>
## Русский · [English](#english)
… те же секции по-русски …

---
**Full Changelog / Полный список изменений:** https://github.com/MikalaiKryvusha/KrinikCam/compare/vПРЕД...vX.Y
```
**Ноты — это ДЕЛЬТА, а НЕ копия README.** Ноты отвечают на ОДИН вопрос: *«что изменилось в ЭТОЙ версии
и стоит ли обновляться?»* — строго дельта этой версии; всё, что описывает продукт вообще, даётся
ССЫЛКОЙ на README, а не копируется (полевой инцидент: 34 КБ нот оказались почти копией README;
переписанные по дельте — 12 КБ, и ни один факт не потерян). Механическая проверка объёма перед
выпуском: **абзац, который можно без правок вставить в README, принадлежит README, а не нотам.**

**Разные документы черпают из разных колодцев:** ноты берут форму из ПРЕДЫДУЩИХ нот ЭТОГО проекта
(`gh release view vПРЕД --json body -q .body` — следуй домашнему стилю), а README берёт форму из
текущего README и других витрин репозиториев Криника. Внутри каждого языка сохраняется НАШ набор
секций (шаблон выше: 🎥 Cameras & scene · 📡 Streaming · 🎞️ Recording · 🌍 Localization · 🐞 Fixes ·
📦 Install) — он и есть наше «что нового», расписанное по темам. Из канона 2.1 добавляются два
элемента: секция **⬆️ Обновление** — когда актуально, и ССЫЛКА на README вместо копирования
описания продукта (что такое KrinikCam и как его начать использовать).

Собери highlights из `git log vПРЕД..HEAD` (сгруппируй по темам, не сырые коммиты), сверься со STATUS и
`*_DONE_*`. Применяй ПОСЛЕ `release.mjs`: `gh release edit vX.Y --notes-file <файл>`. Проверь якоря:
`gh release view vX.Y --json body -q .body | grep -E '<a name=|## English|## Русский'` — переключатели
на месте (их потеря = регресс, EXP «проебал переключатели»).

Если Криник дал релизу имя (Шаг 0) — тем же заходом поправь заголовок:
`gh release edit vX.Y --title "KrinikCam X.Y — <Имя>"` (`release.mjs` ставит нейтральный
`KrinikCam X.Y`), а в ноты внеси строку-источник `codename: <владелец · канал · дата>`. Имени нет —
заголовок остаётся нейтральным, заглушку не выдумываем.

## Шаг 7.9. ГЕЙТ ПУБЛИКАЦИИ — открой отрендеренную страницу и прочитай первый экран ГЛАЗАМИ (KAIF 2.2; исключения структуры — 2.8)

Проверить ИСХОДНИК — не значит проверить ПУБЛИКАЦИЮ. Правила рендера принадлежат чужой среде, и они
разные: **тело GitHub-релиза сохраняет одиночные переносы строк** (перенос на 100 колонках становится
рваным текстом), **README их склеивает**, **PDF перетекает под свою ширину**. Полевой случай:
страница релиза ушла с союзом, висящим в одиночку на строке, и предложением, разрезанным пополам, хотя
исходный файл прошёл четыре зелёных инструмента — дефект пришёл скриншотом от владельца.

```bash
gh release view vX.Y --web   # открой ОПУБЛИКОВАННУЮ страницу, а не файл нот
```
Прочитай первый экран: абзацы целы, переносы там, где ты их задумал, картинка на месте, ссылки
кликабельны, переключатели языка (Шаг 7.5) работают. Механическая половина гейта идёт ДО `gh release
edit`: в файле тела нот **не должно быть двух непустых строк подряд** вне блоков кода, таблиц,
HTML-блоков и комментариев (центрированный логотип, якорь `<a name=…>` перед заголовком и
HTML-комментарий — структура, а не завёрнутая проза).

Правило шире релизов и действует для любой чужой среды — issue, письмо, чат-бот, слайд: узнай её
правило переноса ДО написания, открой результат ПОСЛЕ отправки.

## Шаг 8. Проверка и итог

```bash
gh release view vX.Y                # релиз создан, APK приложен
git log --oneline -3                # виден commit release: X.Y + тег
```
Кратко отчитайся Кринику: версия, ссылка на релиз
(`https://github.com/MikalaiKryvusha/KrinikCam/releases/tag/vX.Y`), что приложен APK. Готово.

## Заметки

- `release.mjs` бампит **minor/major**, а `commit.mjs` — только **build**-номер (`version.json.build`).
  Релиз = новая minor/major; обычные коммиты по ходу = build.
- Если пуш отклонён (non-fast-forward) — `git pull --rebase` и повтори. На шаге 6 это критично: тег уже
  мог создаться локально — проверь `git tag` и при необходимости `git tag -d vX.Y` перед повтором.
- `gh` должен быть залогинен (`gh auth login`). Без него шаг 6 упадёт на `gh release create`.
- НИКОГДА не делай force-push и не удаляй чужие теги/релизы. Если что-то пошло не так на выпуске —
  остановись и покажи Кринику, не «чини» вслепую.
- Не выпускай релиз в автономном режиме (/autoloop) — только по явной просьбе Криника.
