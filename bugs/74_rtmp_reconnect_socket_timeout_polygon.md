## ✅ РАЗГАДКА (2026-07-29, прогон по Wi-Fi днём)

**Планшет уходит с Wi-Fi на сотовую сеть прямо посреди эфира.** Через 30 секунд «linger» Android
окончательно отпускает Wi-Fi-сеть — и вместе с ней умирает RTMP-сокет. Реконнект после этого стучится
на **LAN-адрес Мака `192.168.1.223` уже через сотовую сеть**, где этот адрес недостижим **в принципе** —
отсюда `SocketTimeoutException … after 5000ms` попытка за попыткой при «живой сети».

### Почему прежняя проверка «ушёл на сотовую» дала ложное «исключено»

В таблице ниже строка «Планшет ушёл на сотовую» помечена как исключённая по `dumpsys connectivity`
(«дефолтная сеть — Wi-Fi, VALIDATED»). Замер был верен, но **сделан не в тот момент**: Wi-Fi к тому
времени уже вернулся. Отказ длится ~90 секунд, а `dumpsys` показывает только «сейчас».
**Урок методики:** сетевую гипотезу нельзя проверять срезом состояния — только непрерывным
логом, покрывающим момент отказа.

### Почему это НЕ дефект приложения

- Реконнект отработал **штатно**: бесконечные попытки (уровень 1), эфир воскрес без касания приложения.
- `dropV=0`, `cache=0`, `attempt=0` после восстановления — потерь и залипания нет.
- Watchdog (уровень 3) снова **не срабатывал ни разу** — и правильно: сокет был мёртв, а не «зомби».
- Слабый сигнал как причина **не подтверждён и не опровергнут**. Ближайший замер — `dumpsys wifi`,
  запись `rec[16]` с отметкой **20:07:04**: `rssi=-50 f=5240 sc=100 … score=100`, то есть за
  11 минут ДО ухода сигнал был отличным. **В самом logcat строки RSSI на момент 20:18:39 нет**
  (проверено `grep 'rssi=-50.*score=100'` по логу прогона → 0 совпадений), а `dumpsys` снимался уже
  после возврата Wi-Fi. Поэтому утверждать «в момент ухода сигнал был хорош» нельзя — нужен прогон
  с периодическим снятием RSSI. Это уточнение внесено judge-проходом 2026-07-29.

### Следствия для проекта

1. **Методика прогонов.** Реальные сетевые прогоны — по USB (§10 `plans/21`) **или** с выключенными
   мобильными данными: пока в устройстве активна SIM, Android вправе увести дефолт на LTE в любой
   момент, и любой прогон на LAN-полигон получит ложный «дефект приложения».
2. **Работа E (сетевой колбэк) дороже, чем оценена в `plans/21`.** План ставит её последней с ценностью
   «до ~15 с из окна платформы». Наблюдение показывает другое: при смене сети сокет привязан к УМЕРШЕМУ
   интерфейсу, и «пробуждение» реконнекта на новом — это не экономия секунд, а единственный способ
   быстро вернуть эфир. Переоценка приоритета — **решение уровня владельца**, здесь только факт.
3. **Это ровно боль Криника из вижна** («стримлю из парка»): в поле устройство мечется между сетями
   постоянно. То есть сценарий не лабораторный, а целевой.

### Как воспроизвести/проверить заново

```bash
adb -s 192.168.1.3:5555 logcat -v time > /tmp/net.log &     # ДО прогона, непрерывно
node tools/rtmp-server.mjs start
node tools/ui.mjs cmd go-live-rtmp rtmp://<ip-мака>:1935/live/test
# в момент симптома:
grep -E "Switching to new default network" /tmp/net.log     # покажет транспорт (WIFI / MOBILE[LTE])
grep -E "handleLingerComplete" /tmp/net.log                 # момент отпускания старой сети
```
Признак именно этого класса: между `Switching … MOBILE` и обрывом эфира проходит ~30 секунд linger.

## Симптом

1. Эфир поднимается нормально: `connected ✓`, сервер печатает `is publishing`, 2 дорожки.
2. Через **2–4 секунды** — `RTMP[0] connection failed: Error send packet, Broken pipe`;
   на стороне сервера: `closed: read tcp …: read: connection reset by peer`.
3. Дальше реконнект **не может установить TCP вообще**:
   `java.net.SocketTimeoutException: failed to connect to /192.168.1.223 (port 1935) … after 5000ms`,
   попытка за попыткой (проверено до attempt=7).

## Странность, которая и есть ключ к причине

**Короткое TCP-соединение из shell устройства проходит мгновенно, а RTMP-сессия того же устройства
рвётся через пару секунд и потом не устанавливается вовсе.** То есть отказ зависит не от
достижимости хоста, а от НАГРУЗКИ или от состояния сетевого стека конкретного процесса.

Живые гипотезы (ни одна не проверена — не выдумывать причину):
1. **Wi-Fi-канал/чип.** Ночная деградация 5 ГГц, энергосбережение Wi-Fi на планшете, потери при
   заливке ~4 Мбит/с вверх. Проверяется прогоном **по USB** (`plans/21` §10 прямо это требует) и
   замером аплинка отдельным инструментом.
2. **Состояние сокетов в процессе приложения** после серии из ~10 старт/стоп-циклов и двух
   watchdog-реконнектов за сессию (утечка/подвисшие дескрипторы в RootEncoder).
3. **Мак** (сетевой стек/энергосбережение ноутбука ночью) — хотя локальные подключения к серверу
   в тот же момент проходили.

## Доказательство «watchdog не причастен» (по требованию верификации)

Утверждение проверяемо командой на логах прогонов (файлы прогонов — вне git, `/tmp/stepB2.log`,
`/tmp/stepB3.log`, копия в скрэтчпаде сессии):

```
grep -c 'watchdog\[' /tmp/stepB2.log   → 0
grep -c 'watchdog\[' /tmp/stepB3.log   → 0
```

То есть в обоих проблемных прогонах строка срабатывания (`watchdog[i]: отправка стоит …`) не
появлялась ни разу, а реконнекты порождались библиотечным `onConnectionFailed`
(`Error send packet, Broken pipe`). Формально это доказывает лишь, что **в наблюдавшемся окне лога**
срабатываний не было; логи прогонов к репозиторию не приложены (правило `.gitignore` для девайс-логов),
поэтому при повторной проверке команду надо выполнить заново на свежем прогоне.
