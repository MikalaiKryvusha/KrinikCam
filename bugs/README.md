# `bugs/` — дефекты, трудности, поломки

По документу на дефект: симптом, детерминированное репро, форензика, root cause / гипотезы, история
фикса, статус. Долговечный беклог багов самого агента — ничего не теряется, любой баг может подхватить
«с холода» будущая сессия. Один баг — один файл `NN_<name>.md`.

**Кринику (владельцу):** можешь завести баг простыми словами (что не так, как воспроизвести) — агент
приведёт его к канону. Смотри сюда, чтобы видеть известные дефекты и их статусы.

**ИИ-агенту:** наткнулся на дефект в ходе работы/теста — заведи документ по канону (навык
`/report-bug`; метод — `BUG_FIXING_FRAMEWORK.md`), даже на мелкий. Документ бага несёт НАБЛЮДАЕМЫЙ
критерий приёмки фикса — что будет ВИДНО работающим после фикса (`REQUIREMENTS_FRAMEWORK.md`). Пока
баг открыт — без тега `DONE`. Починен **и проверен** — `git mv NN_x.md NN_DONE_x.md` + секция
`## ✅ STATUS: DONE (дата и время)` (канонический английский маркер с KAIF 2.9; старые доки с
`СТАТУС` не переписываем) с двумя отдельными строками `Hygiene:` и `Functional run:` (что прошли руками
пользователя, на каком устройстве, что ПРОЧИТАЛИ — или `NONE` = «починено, не протестировано»;
`TESTING_FRAMEWORK.md`). После 3 неудачных слепых попыток фикса — стоп, переключайся на исследование
(`/bug-research`).

**Поддиректория `bugs/KAIF/`** — дефекты и запросы на улучшение о **самом фреймворке KAIF**, а не о
KrinikCam. Когда сбой восходит к дыре в KAIF (правило ввело в заблуждение, не хватило гвардрейла,
сломалась машинерия) — заводи документ там по тому же канону, **строго на английском** (адресат —
разработчик KAIF). Перед заведением — дедупликация: поищи в `bugs/KAIF/` и в issue-трекере origin.
У нас tracking = `origin`, поэтому заведённый тикет ОТПРАВЛЯЕТСЯ тем же ходом:
`node .kaif/kaif-core.mjs report bugs/KAIF/NN_<имя>.md` (постоянная авторизация владельца KAIF, KAIF 2.7).
