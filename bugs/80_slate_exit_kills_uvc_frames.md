# Bug 80 — выход из сетевого слейта НАСМЕРТЬ останавливает кадры UVC → в эфир навсегда уходит брендовая заглушка

**Статус:** ✅ **ЗАКРЫТ 2026-08-02** — фикс применён в ОБОИХ местах класса, приёмка наблюдением
(6 циклов из 6), гард на класс добавлен и проверен на сломанной версии
**Версия:** 0.8 (52)-debug
**Устройство:** Samsung Galaxy A51 (`R58N615KXZZ`), Android 13 / SDK 33, источник — **UVC Emeet Piko+**
(`328f:00c7`) на питаемом хабе
**Найден:** 2026-08-02, приёмка шага **C6** `plans/21` (плашка слейта на кадре с сервера)
**Класс:** тихий отказ источника — ни одной строки в логе, все сетевые счётчики зелёные

## 1. Симптом

После нескольких входов-выходов в **сетевой слейт** (уровень 4, `plans/21` работа C) слой UVC-камеры
перестаёт получать кадры **навсегда**. Через `STANDBY_HOLD_MS` (10 с) поверх всплывает брендовая
заглушка «Please stand by / Пожалуйста, подождите», и **она уже не гаснет** — в эфир уходит она.

Коварство в том, что по всем метрикам эфир ЗДОРОВ: `Live`, `cache=0`, `dropV=0`, битрейт ~550–900
кбит/с, сокет жив, звук идёт. Приложение исправно кодирует и отправляет — **заглушку**. Ровно тот
класс, что `bugs/76`: «по всем счётчикам эфир был здоров, дефект нашли ГЛАЗА».

Прямое нарушение вижна: механизм, задуманный как защита зрителя на просадке сети, сам лишает
зрителя картинки — причём необратимо, до ручного переоткрытия источника.

## 2. Репро (воспроизводится стабильно, 2 прогона из 2; во втором хватило ДВУХ циклов)

```bash
# Канал ШИРОКИЙ (дроссель снят) — сеть в репро не участвует вообще

# Цикл: слейт вкл 5 с → выкл 6 с → снять кадр С СЕРВЕРА
node tools/ui.mjs cmd simulate-slate on;  sleep 5
node tools/ui.mjs cmd simulate-slate off; sleep 6
ffmpeg -y -i rtmp://127.0.0.1:1935/live/test -t 2 -vf fps=1 /tmp/f_%02d.png
```

**Критерий наблюдения** — доля «небледных» пикселей кадра (живая картинка с монитора ≫ 20 %,
брендовая заглушка ≈ 2–4 %):

| Замер | Живость кадра с сервера |
|---|---|
| базовая линия (слейта ещё не было) | **74.0 %** |
| после цикла 1 | 73.8 % |
| **после цикла 2** | **2.3 %** ← картинка не вернулась |

Скрипт репро — `slate-cycle.mjs` (скрэтчпад сессии), метрика считается кодом, не глазами.

**Камера при этом исправна:** `select-source none` → `select-source uvc` немедленно возвращает
картинку (**73.9 %**). То есть зависание ПРОГРАММНОЕ, а не отвал железа или USB.

## 3. Форензика — что говорит лог (и чего он НЕ говорит)

Главная улика — **тишина**. За весь отказ в логе нет ни `enterCameraStandby`, ни `USB disconnected`,
ни ошибок libuvc. Только штатные строки слейта:

```
15:34:09.956 CompositorVideoSource: сетевой слейт: ВКЛ — кадр заморожен
15:34:15.xxx CompositorVideoSource: сетевой слейт: ВЫКЛ — картинка живая     ← после этого кадры встают
15:34:16.430 RtmpStreamer: пульс[0] Live bitrate=979kbps cache=0 sentV=7977 dropV=0 congested=false
```

`sentV` продолжает расти — энкодер жив и гонит в эфир замороженный кадр, а затем заглушку.
Ни один существующий гард такой отказ не видит: они все смотрят на СЕТЬ, а сломался ИСТОЧНИК.

## 4. Root cause (найден чтением кода)

`CompositorVideoSource.setNetworkSlate` (`:500-507`):

```kotlin
fun setNetworkSlate(active: Boolean) {
    if (netSlateActive == active) return
    netSlateActive = active
    // Выход из слейта: сбрасываем «протухший» кадр, чтобы видимая картинка не дёрнулась старым
    // содержимым — тот же приём, что в exitCameraStandby.
    if (!active) handler?.post { cameraSlots.values.forEach { it.newFrame = false } }   // ← ЗДЕСЬ
    ...
}
```

`newFrame` — это **единственный** способ узнать, что кадр доступен: его взводит
`setOnFrameAvailableListener`, и колбэк приходит **ровно один раз на кадр**. Потребитель забирает
кадр только под этим флагом (`:297`: `if (st != null && newFrame && !frozen)`).

Сброс флага в произвольный момент означает: **уведомление о уже лежащем в очереди буфере
выброшено**. Если продюсер в этот момент ждёт освобождения буфера, чтобы поставить следующий кадр,
нового `onFrameAvailable` не будет никогда:

> потребитель ждёт уведомления → уведомление выброшено → продюсер ждёт освобождения буфера →
> буфер освободит только потребитель. **Взаимная блокировка, тихая и вечная.**

Дальше механика видна прямо в коде: `lastFrameAtMs` перестаёт обновляться (`:300`) → `waited`
растёт → на 10 с `wantStandby` становится `true` (`:316`) → `standbyAlpha` уезжает в 1 (`:324-326`)
→ слой рисуется заглушкой (`:918-922`). Всё «по правилам», просто источник уже мёртв.

**Почему не поймали 29 июля.** Приёмка C1 прошла на другом источнике, и в шапке `setNetworkSlate`
стоит `[TESTED: 2026-07-29 …]` с честными числами (`standbyAlpha` ≡ 0.0, `framesConsumed` 415→1866).
Маркер не врёт — он просто снят на источнике с другой дисциплиной буферов. У UVC (libuvc пишет в
`Surface` напрямую, очередь короткая) пропущенное уведомление фатально; у device-камеры и виртуалки
следующий колбэк приходил всё равно, и дефект не проявлялся. Это же объясняет **«открытый риск C1»**
(`plans/21` C1: «в одном раннем прогоне на UVC наблюдалась брендовая заглушка на чёрном фоне,
воспроизвести не удалось, проверить отдельно на UVC в C6») — риск был настоящий, и вот он.

## 5. TWINS — тот же паттерн в соседней функции

`TWINS: искал сброс newFrame вне точки потребления — найдено 1 другое место:`

- `CompositorVideoSource.exitCameraStandby` (`:474-477`):
  `handler?.post { cameraSlots[layerId]?.let { it.frozen = false; it.newFrame = false } }`

Тот же приём, та же цена — и на него прямо ссылается комментарий в `setNetworkSlate` («тот же приём,
что в exitCameraStandby»). Отличие: `exitCameraStandby` зовётся, когда источник ВОЗВРАЩАЕТСЯ после
отрыва, и следом идёт переоткрытие продюсера, которое обычно взводит колбэк заново, — поэтому там
дефект маскируется. Чинить надо **класс**, а не экземпляр.

## 6. План фикса

`INTENT:` код при выходе из слейта сбрасывает `newFrame`, чтобы не показать протухший кадр; задача
ожидает, что после выхода картинка ОЖИВЁТ; спека (`plans/21` C1, `interviews/interview_012` В1)
говорит: «`false` — немедленно вернуть живую картинку». Расхождение — в цене приёма: он выбрасывает
уведомление, без которого живая картинка не возвращается вовсе.

- [x] **Ф1. СДЕЛАНО.** Не выбрасывать уведомление. Вместо `newFrame = false` — взвести `newFrame = true`:
      попытка забрать кадр безопасна (`updateTexImage` под `runCatching`, `:298`), а лишний заход
      стоит один кадр. Страх «дёрнется старым содержимым» цену не оправдывает: `updateTexImage`
      отдаёт САМЫЙ СВЕЖИЙ доступный буфер, то есть «старое» — это кадр возрастом ≤ 33 мс, которого
      зритель и так не отличит от текущего.
- [x] **Ф2. СДЕЛАНО.** Тот же фикс в `exitCameraStandby` (близнец из §5) — класс, а не экземпляр.
- [x] **Ф3. СДЕЛАНО и ПРОВЕРЕНО НА СЛОМАННОЙ ВЕРСИИ.** `CompositorVideoSource.oldestFrameAgeMs` —
      возраст кадра самого протухшего слоя, считается на GL-потоке рядом с `anyLiveCameraFrame`;
      печатается в пульсе как `src=Nмс`. Все прочие числа пульса про СЕТЬ — это единственное про
      ИСТОЧНИК.
      **Гард скормлен собственному дефекту:** временно вернул `newFrame = false`, пересобрал, прогнал
      3 цикла — `src` пополз монотонно **2308 → 3281 → 4282 → 5317 мс** при `Live`, `cache=0`,
      `dropV=0` и битрейте 5.9 Мбит/с. После возврата фикса на том же сценарии `src` ≤ 43 мс.
      То есть гард умеет краснеть, и краснеет ровно на этом классе.
- [x] **Ф4. ПРОЙДЕНА.** `slate-cycle.mjs`, **6 циклов подряд** на UVC (0.8 (52)-debug, A51):

      | цикл | 1 | 2 | 3 | 4 | 5 | 6 |
      |---|---|---|---|---|---|---|
      | живость после выхода из слейта | 51.2 % | 73.2 % | 73.1 % | 73.0 % | 73.0 % | 73.0 % |

      Базовая линия до слейта — 51.1 %. До фикса тот же прогон умирал на цикле 2 (2.3 %).
      ⏳ Повтор на device-камере — НЕ проводился (на A51 фронталка занята другим классом ограничений,
      см. STATUS про конфликт камер); класс там и раньше работал, риск регресса низкий, но честно:
      не проверено.
- [x] **Ф5. СДЕЛАНО.** `[TESTED: 2026-07-29 …]` в шапке `setNetworkSlate` заменён на приёмку от
      2026-08-02 (A51 + UVC, 6 циклов, числа выше). Прежний маркер оставлен в комментарии как урок:
      его числа не были ложью — они были сняты на источнике с ДРУГОЙ дисциплиной буферов, и зелёный
      маркер ровно этим и скрывал дефект.

## 8. Решения, принятые без владельца

1. Метрика «живость кадра» (доля пикселей ярче 60 по любому каналу) — прокси агента, а не решение
   Криника. Она нужна лишь чтобы отличить заглушку от картинки числом, а не на глаз; порог
   выбран по замеру: заглушка 2.3–2.4 %, живая картинка 73.8–74.0 % — разрыв в 30 раз.
2. Направление фикса (взвести флаг вместо сброса) выбрано как минимальное; альтернатива «завести
   отдельный флаг протухания» плодит сущность ради страха, который замером не подтверждён.
