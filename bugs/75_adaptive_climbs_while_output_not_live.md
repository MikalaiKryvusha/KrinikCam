## 1. Симптом

На канале, который **жив, но узок** (300 кбит/с при цели 4000), эфир не деградирует и не стабилизируется,
а входит в **петлю реконнекта, которая не сходится**. Цикл повторяется каждые ~11–13 секунд
бесконечно. Зритель видит поток, который постоянно рвётся и переподключается, вместо ожидаемого
«картинка похуже, но идёт».

Это прямое нарушение вижна Криника «**эфир завершает только кнопка Стоп**» (`ideas/43`): формально
кнопку никто не нажимал, но и эфира — нет.

## 4. Root cause — подтверждён исходником

`…/rtmp/RtmpStreamer.kt:727-751` (номера строк — ПОСЛЕ фикса; до него блок начинался на `:718`)

```kotlin
val anyCongested = outputStates.values.any { it.phase == OutputPhase.Live && it.congested }
val next = when {
    anyCongested ->                                    // ← ветка СНИЖЕНИЯ требует Live
        (currentVideoBitrateBps * (100 - ADAPTIVE_DECREASE_PERCENT) / 100)
            .coerceAtLeast(floorVideoBitrateBps)
    currentVideoBitrateBps < targetVideoBitrateBps ->   // ← ветка ВОССТАНОВЛЕНИЯ Live НЕ требует
        (currentVideoBitrateBps + targetVideoBitrateBps * ADAPTIVE_RECOVER_PERCENT / 100)
            .coerceAtMost(targetVideoBitrateBps)
    else -> currentVideoBitrateBps
}
```

**Гард асимметричен.** Условие `phase == Live` стоит только в ветке снижения. В фазе `Reconnecting`
живых выходов нет вовсе → `anyCongested = false` → управление проваливается в ветку восстановления,
которая растит битрейт **на основании отсутствия сведений**, и лог при этом утверждает «канал чист»
(лог-строка в том же блоке) — то есть говорит неправду о канале, о котором ничего не знает.

Это ровно тот класс, который уже ловили в этом проекте на шаге C3 (`plans/21`): «лог при
ВЫКЛючении слейта подставлял причину ВКЛючения». Одна и та же ошибка формы — **вывод о состоянии
канала делается из значения, которое в этой фазе просто не определено**.

**Почему это не всплывало раньше.** Ни один прежний сценарий приёмки не создаёт долгого узкого,
но ЖИВОГО канала: `simulate-congestion` держит затык вечно и не запускает восстановление
(`plans/21` A4b говорит это прямым текстом), `freeze`/`stop` полигона убивают сокет целиком, а на
чистом эфире восстановление всегда законно. Дефект живёт ровно в пересечении «выход не Live» и
«битрейт ниже цели», куда попадают только реальные обрывы на узком канале.

## 6. План фикса

- [x] **Ф1. СДЕЛАНО** — симметричный гард (`anyLive`), ~2 строки. Ветка восстановления обязана
      требовать того же, что ветка снижения: хотя бы один выход в `Live`.

      ```kotlin
      val anyLive = outputStates.values.any { it.phase == OutputPhase.Live }
      val anyCongested = outputStates.values.any { it.phase == OutputPhase.Live && it.congested }
      val next = when {
          anyCongested -> …снижаем…
          anyLive && currentVideoBitrateBps < targetVideoBitrateBps -> …растим…
          else -> currentVideoBitrateBps
      }
      ```

      Ни нового поля, ни нового флага, ни новой константы — одно условие, приведённое к симметрии
      с соседним (PHILOSOPHY: не множить сущности; убираем спец-случай, а не добавляем).

- [x] **Ф2. ПРОЙДЕН** — гард проверен на СЛОМАННОЙ версии: строк «канал чист — восстанавливаем»
      в фазе не-Live было **5** (лог `k1b`), после фикса **0** (лог `k1c`). Команда гарда —
      awk по логу: помним последнюю фазу из пульса, считаем строки восстановления вне `Live`.
      Исходная формулировка шага: Проверить фикс НА СЛОМАННОЙ версии: прогон K1 обязан давать
      ≥1 строку «канал чист — восстанавливаем» в фазе Reconnecting ДО фикса и ровно 0 ПОСЛЕ.
      Гард, который ни разу не краснел, ничего не доказывает (`BUG_FIXING_FRAMEWORK.md` → Гарды).

- [x] **Ф3. ПРОЙДЕНА** — репро §2 повторено на фиксе (прогон 15:44–15:49, селфи-камера): в фазе
      `Reconnecting` ни одной строки восстановления; лестница стоит на месте, пока эфира нет.
      Исходная формулировка шага: повтор репро §2. Критерий — в фазе Reconnecting нет ни одной
      строки восстановления; период между реконнектами перестаёт быть постоянным ~12 с.

## 7. Что фикс Ф1 НЕ чинит — и это надо решить отдельно

Ф1 убирает ложь («канал чист» при мёртвом эфире) и останавливает разгон. Но **петля реконнекта
сойдётся не полностью**: после фикса эфир воскреснет на том битрейте, на котором умер (в замере —
2048 кбит/с), а это всё ещё в 7 раз больше канала. Цикл станет медленнее, но не исчезнет.

Полное решение упирается в вопрос, **на каком битрейте возобновлять эфир после обрыва, вызванного
сетью**. Кандидаты (агент их НЕ выбирает — это ближе к вижну, чем к коду):

| Вариант | Смысл | Цена |
|---|---|---|
| (а) стартовать с пола профиля | самый быстрый выход в стабильный эфир | картинка резко хуже даже если обрыв был случайным |
| (б) снизить на один шаг адаптива | консервативно, симметрично затыку | на узком канале сходится долго (много обрывов) |
| (в) помнить последний битрейт, на котором эфир жил ≥N секунд | «умно» по духу GOAL | новая сущность-память, спец-случай |

👉 **Вопрос вынесен Кринику отдельным документом — `interviews/interview_015`** (канон KAIF 2.1:
место вопросов — только `interviews/`). До ответа реализуется только Ф1.

✅ **ОТВЕТЫ ПОЛУЧЕНЫ 2026-07-31:** В1 = **(а)** пол профиля · В2 = **(в)** от текущего + пауза ·
В3 = **(в)** слейт не трогать. Реализованы шагами Ф5–Ф7 выше. Что это дало и чего НЕ дало — §10.

## 8. История инструмента (почему баг дожил до 2026-07-31)

Сценарий K1 не проверялся ни разу, потому что для него нужен дроссель, а дросселя не было.
`tools/net-chaos.mjs` написан 2026-07-29 с маркером `[NOT-TESTED]` и **сам содержал два дефекта**,
из-за которых был непригоден именно на рабочей полосе (оба починены 2026-07-31, коммит `ea80a84`):

1. Токен-бакет требовал токенов на **целый чанк TCP** при капе в одну секунду полосы. На 300 кбит/с
   кап = 37 500 Б, чанк = 65 536 Б → условие не выполнялось никогда, выход = 0 байт. Мёртвой была
   всякая полоса ниже ~524 кбит/с.
2. Глубина очереди задавалась **в чанках (2048)**, что на 300 кбит/с даёт ~8 МБ ≈ 3.5 минуты
   вещания. Приложение не чувствовало сужения канала **целую минуту**, и первый прогон измерял
   буфер инструмента, а не поведение приложения. Заменено на буфер в **миллисекундах полосы**
   (`--queue-ms`, дефолт 1000).

Урок уровня подхода — в `EXPERIENCE.md`.

## 9. Решения, принятые без владельца

1. Диагностический прогон выполнен с **выключенными мобильными данными** на планшете
   (`svc data disable`, откат `svc data enable`) — иначе Android вправе увести маршрут на LTE и
   дать ложный «дефект приложения» (`bugs/74`, EXP-0034). Исходное состояние — `mobile_data1 = 1`.
2. Глубина буфера узкого места в дросселе — **1 секунда полосы**, как защитимая модель очереди
   бутылочного горлышка. Число агента, не владельца; правится флагом `--queue-ms`.
3. Порог полосы для репро — **300 кбит/с**: он ниже суммы «пол видео 250 + звук 128 = 378», то есть
   заведомо не влезает даже на полу. Выбран сознательно, чтобы адресовать дверь (б).
4. Вопрос «на каком битрейте возобновлять эфир после сетевого обрыва» агент **не решает** —
   вынесен в `interviews/interview_015`.
5. **«Сетевой обрыв» = обрыв ЛЮБОГО выхода, который был в фазе `Live`** — без попытки отличить
   «канал не тянет» от «сервер перезагрузился». Отличить их в момент обрыва приложению нечем:
   `congested` к этой миллисекунде уже могло сброситься, а причина от библиотеки одинакова.
   Эвристика по признакам затыка молча возвращала бы петлю там, где `hasCongestion()` не успел
   сработать. Цена (случайный блип тоже роняет картинку на пол) названа владельцу прямо в
   `interview_015` в клетке варианта (а), который он и выбрал.
6. **Шаг восстановления 20%** — число агента. Владелец выбрал ФОРМУ («от текущего»), процент в
   ответе стоял примером. 20% симметричны снижению −20%; при этом −20% и +20% не обратны
   (0.8 × 1.2 = 0.96), то есть подъём чуть консервативнее спуска — асимметрия в пользу живучести.
7. **Пауза 10 с** — число агента, выведенное из watchdog, а не из головы: обречённый эфир умирает
   через `WATCHDOG_STALL_MS` = 6 с после остановки отправки, значит пауза обязана быть длиннее
   этого окна, иначе разгоняем поток, который ещё не доказал, что живёт. 10 с = 6 с + запас на
   дискретность шага адаптива (2 с). Замер дал фактические 11.8 с.
8. **Правка битрейта в момент обрыва, а не на успехе реконнекта.** Энкодер на retriable-пути не
   гасится и работает всю фазу `Reconnecting`, поэтому воскресший сокет с первого пакета получает
   поток на полу — и между фазами не нужно ничего помнить (никакой новой сущности-памяти, которую
   владелец отклонил вариантом (в)). Подтверждено наблюдением: пульс после реконнекта 369 кбит/с,
   а не 2048.

**Итог честно:** петля **не исчезла, а замедлилась в ~4.5 раза** (12 с → 53–59 с), и эфир между

**Причина остатка — не в этих фиксах, а в конструкции лестницы** (то же наблюдение, что `plans/21`
A4b: «лестница проигрывает гонку по построению»), и теперь у него есть числа:

1. **Лестница не помнит, на чём эфир умер, и идёт к цели.** «Дальше поднимать как обычно» —
   дословно ответ В1(а). За 30 с она уходит на 1857 кбит/с при видео-ёмкости канала ≈322
   (450 − 128 звука), то есть **перелетает ёмкость в 5.7 раза**.
2. **Затык виден с опозданием, пропорциональным перелёту.** На 360–518 кбит/с (уже выше ёмкости)

3. **Спуск не успевает за смертью сокета.** От первого затыка до пола 9 шагов × 2 с = **16 с**,

отдельную фичу. Новое здесь — факт, которого у него при том решении не было: с (а)+(в) эфир на

## 11. КРЫША ЛЕСТНИЦЫ — ответ владельца реализован и замерен (2026-07-31, вечер, лог `k1f`)

**Ответ Криника (`interview_016` В1):** вариант **(а)** — крыша по доказанному уровню + пробные
шаги; уточнение владельца дословно: «*можно проверять чаще, например раз в минуту*».

**Реализовано** (`RtmpStreamer.adaptiveBitrateStep` + `onLiveOutputBroken`): крышу ставит сам затык
(уровень после снижения); пока затыка не было — крыши нет вовсе (широкий канал ведёт себя как
раньше); раз в `ADAPTIVE_PROBE_MS` = 60 с спокойного эфира крыша поднимается на шаг; обрыв сажает
крышу на доказанный уровень (`ADAPTIVE_PROVEN_MS` = 30 с без затыка), а если доказать не успели — на
пол. Крыша живёт один эфир: Стоп → Старт снимает её.

**Прогон на СЕЛФИ-камере** (замечание Криника: виртуалка кодируется в разы легче реальной картинки,
и сетевой замер на ней — замер не того; плюс на реальной камере находятся баги вроде `bugs/76`),

## 12. ЛЕНТА ЗРИТЕЛЯ — приёмка ГЛАЗАМИ, а не логом (новый инструмент)

Криник: «*можешь тест с просадкой сети стримить в файл — чтобы посмотреть, как бы это на стороне
зрителей выглядело?*». Оснастка этого не умела, теперь умеет: **`tools/viewer-tape.mjs`** пишет поток
**С СЕРВЕРА** (не с телефона: на телефоне картинка живая всегда, а зритель видит то, что вылезло из
сокета), переживает обрывы кусками и склеивает их в одну ленту с ЧЕСТНЫМИ провалами.

Лента прогона выше: 209.7 с, три куска эфира, **40.2 с замершей картинки** и **3.9 с полного
отсутствия эфира**. Обе беды на ленте подписаны прямо в кадре («картинка встала — 17.7 с»).

Две ловушки инструмента, обе оплачены и записаны в его шапке: одной командой ffmpeg непрерывную
ленту снять нельзя (на обрыве он получает EOF и выходит), а длительность провала нельзя считать по
меткам процессов ffmpeg — источник правды тут лог приложения (`watchdog[0]` → `connected ✓`).
