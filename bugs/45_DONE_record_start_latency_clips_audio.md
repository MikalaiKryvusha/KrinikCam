# Bug 45 — Запись видео в файл стартует с большой задержкой (режет начало фразы)

> Заведён: 2026-07-18 (наблюдение Криника при живой записи). Приоритет: ВЫСОКИЙ для UX —
> «думал, запись уже идёт, а начало моей фразы отрезало».

## Симптом

Криник нажал «Запись», бейдж/индикатор показал, что запись идёт — но по факту файл начал писаться с
заметной задержкой, и **начало произнесённой фразы в записи отсутствует**. То есть индикация «идёт
запись» появляется РАНЬШЕ, чем реально пишутся кадры/звук.

## Репро (детерминированное)

1. `stream-to-file on`, затем нажать «Запись» (или харнес `go-live`) и СРАЗУ говорить/хлопнуть.
2. Остановить, вытащить mp4, посмотреть первые секунды: начало обрезано / индикатор был «активен»
   до появления первого кадра.
3. Замер: сравнить timestamp «показали LIVE-бейдж» (`_state.value = Live()`) с первым реально
   записанным кадром (RecordController → RECORDING / первый муксенный сэмпл).

## Root cause (гипотезы)

В `RtmpStreamer.startRecordToFile` индикация выставляется НЕМЕДЛЕННО:
`_state.value = StreamState.Live()` идёт СРАЗУ после `stream.startRecord(path)`, но до этого момента
успевает пройти дорогая настройка: `stopPreview()` → `configureCaptureRotation` (**рестарт
video-source `changeVideoSource` под новую геометрию энкодера**) → `prepareVideo` + `prepareAudio` →
`startRecord` → и только потом GL-пайплайн реально прогревается (`schedulePreviewRestoreAfterStream`
ждёт `gl.isRunning` до 5с). Плюс MediaCodec/аудио-record стартуют не мгновенно (в логах приёмки было
видно `AudioRecord: dead IAudioRecord ... creating a new one` — переинициализация записи звука).
Итог: MediaMuxer получает первый семпл спустя сотни мс–секунду после того, как юзер уже говорит.

## План фикса

> Детальный план исполнения → **`plans/15_record_start_latency.md`**. Ниже — краткая версия.

1. **Замер сначала** (BUG_FIXING: сначала воспроизвести и измерить): залогировать Δ между `startRecord`
   и первым `onStatusChange(RECORDING)` / первым видеокадром в муксер; понять, где основная задержка
   (source-restart? аудио-init? GL-прогрев?).
2. **Индикация по факту, а не по намерению:** переключать UI в «идёт запись» ТОЛЬКО по
   `RecordController.Status.RECORDING` (первый реальный семпл), а до этого показывать «подготовка…».
   Тогда юзер не заговорит в пустоту. (Дешёвый, честный фикс — точно входит.)
3. **Сократить задержку старта:** если основной вклад — рестарт video-source в `configureCaptureRotation`
   при записи (геометрия энкодера обычно = превью), пропускать `changeVideoSource`, когда размеры не
   поменялись. Возможно держать энкодер «тёплым»/пред-прогревать GL. Аккуратно (не сломать поворот).
4. **Приёмка:** записать с хлопком в момент старта → первый кадр/звук на месте (хлопок слышен/виден в
   начале); замер Δ старта до и после (должен упасть, и/или индикатор совпадать с реальным началом).

## Связи

Тот же путь записи, что idea 10/11/17. Не путать с адаптером битрейта (idea 37) — там при записи
target=0, адаптер выключен.

## ✅ ИСПРАВЛЕНО 2026-07-25 (сессия «лёгкие-но-полезные», тест на виртуалке — без UVC)

### S1 — Замер (сначала измерить)
Инструментировал `startRecordToFile` фазовым таймингом + Δ до первого реального семпла. Два прогона
на виртуалке (720p, H264):

| Фаза | Прогон 1 | Прогон 2 |
|------|---------:|---------:|
| `stopPreview` | 64 мс | 95 мс |
| `configureCaptureRotation` (prepareVideo + changeVideoSource) | 113 мс | 60 мс |
| `prepareAudio` | 148 мс | 30 мс |
| `startRecord` | 143 мс | 55 мс |
| **Δ до первого записанного семпла (RECORDING)** | **2769 мс** | **2468 мс** |

**Гипотезы из тикета опровергнуты:** вся синхронная настройка — лишь ~470 мс, рестарт video-source и
init аудио НЕ были главным вкладом. GL был готов через 0 мс, превью переподцеплено на ~950 мс, а
видеокадры шли в энкодер с ~44.6 (по `PipelineWatcher`) — то есть ~2.3 с кадров и звука
**кодировались и выбрасывались**.

### Root cause (сверен байткодом RootEncoder 2.4.7, а не по памяти)
`AndroidMuxerRecordController.recordVideo` добавляет видеотрек и переводит статус в `RECORDING`
**только при совпадении трёх условий**: `status == STARTED` И известны ОБА формата (видео+аудио) И
пришедший буфер — **КЛЮЧЕВОЙ КАДР** (`flags == 1` либо `isKeyFrame(buffer)`).

Первый IDR энкодера проскакивает, пока аудиоформат ещё не пришёл (окно десятков мс), а следующий
ключевой кадр — только через `iFrameInterval = 2 c` из `prepareVideo`. Отсюда стабильные ~2.3–2.5 с:
**это не «медленная инициализация», а ожидание следующего кадра по GOP.**

### Фикс
1. **S2 — честная индикация (главное для UX).** `StreamState.Connecting` стал `data class` с флагом
   `isRecording`. `startRecordToFile` больше НЕ ставит `Live` сразу: ставит фазу подготовки, а бейдж
   «ЗАПИСЬ» + таймер поднимает **только `recordListener` по первому реальному `RECORDING`**. Тикер
   эфира тоже стартует там — таймер считает реальное время записи, а не время подготовки.
   UI: пилюля «● ПОДГОТОВКА» (запись) / «● ПОДКЛЮЧЕНИЕ» (эфир) — янтарная, с дышащей точкой, без
   таймера и битрейта (их ещё не существует). Меню FAB в фазе подготовки даёт «Стоп», а не «Запись».
2. **S3 — сокращение прогрева.** После `startRecord` дёргаем штатный `StreamBase.requestKeyframe()`
   серией коротких попыток (12 × 150 мс, цикл сам гаснет по приходу `RECORDING`) — не ждём следующий
   IDR по GOP. Серия нужна из-за гонки с аудиоформатом: IDR раньше аудиоформата мухер выбрасывает.
   `iFrameInterval` НЕ трогали — 2 с GOP корректен для стрима.

### Приёмка (S4) — наблюдением, на устройстве
- **Прогрев: 2769/2468 мс → 559/605 мс** (≈5×) — по логам двух прогонов до и после.
- **Индикация честная:** видеозахват экрана планшета, нарезка 6 к/с → пусто → «● ПОДГОТОВКА» →
  «● ЗАПИСЬ • 00:00 • …» (таймер стартует с нуля в момент реального старта).
- **Вариант эфира:** `go-live-rtmp` на кривой URL → пилюля «○ ПОДКЛЮЧЕНИЕ» (скриншот).
- **Регресса нет:** записанный файл валиден (h264 1280×720, 933 кадра + aac, `start_time` обеих
  дорожек 0, длительности сходятся); `smoke.mjs` PASS (1920×1080, 168 кадров); юниты
  `:feature:streaming` + `:data:profiles` зелёные.

### Решения, принятые без владельца (KAIF 1.6)
- **Пилюля подготовки показывается и для ЭФИРА, не только для записи** (`Connecting` был у эфира и
  раньше, но виджет его не рисовал). Та же ложь по смыслу, тот же виджет — сделал заодно. Откатить
  = вернуть `visible = streamState.isLive`.
- **Тон пилюли — приглушённо-янтарный** (`0xFFB26A00`), форма/типографика как у live-пилюли. Не
  спрашивал: это не новая сущность, а состояние существующего виджета.
- **Меню FAB в фазе подготовки даёт «Стоп»** (было «В эфир»/«Запись») — чтобы повторное нажатие не
  било вслепую. Затрагивает и эфир в фазе подключения.
- **Зависшая фаза подготовки НЕ промоутится в Live по таймауту.** Если первый семпл не пришёл за 5 с,
  пишем предупреждение в лог, но бейдж честно висит «ПОДГОТОВКА» — врать по таймауту значило бы
  вернуть исходный баг. Остановка при этом доступна.
- **Не менял `iFrameInterval`.** Уменьшение GOP «на всякий случай» ухудшило бы стрим; причина
  устранена запросом ключевого кадра.

### Побочная находка (отдельный дефект, не правил здесь)
На бейдже записи битрейт периодически проваливается в «0,0 Mbps»: секундный тикер (idea 37)
пересчитывает `bitrateKbps` как сумму по RTMP-выходам, а при записи выходов нет → 0, и следующий
`onNewBitrate` возвращает значение. Пре-существующее (тикер жил так и до этого фикса), видно на
нарезке кадров приёмки. → заведён отдельный баг.
